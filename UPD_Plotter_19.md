
# UPD_Plotter_19 — ускорение печати и геометрия слов

## Цель

Сильно сократить реальное время печати текста плоттером за счёт уменьшения количества подъёмов пера и холостых перемещений. Добавить отдельный агрессивный режим, в котором допустимо повторно проходить некоторые участки буквы, если благодаря этому слово можно написать примерно за **1–2 непрерывных прохода пера**.

Одновременно исправить проблемы с аномально большими расстояниями между отдельными словами и со знаками препинания.

---

# Правила работы Codex

Эти правила обязательны на протяжении всего `UPD_Plotter_19`.

1. Работать **в текущей исходной ветке**. Новую ветку не создавать.
2. Не проводить большой повторный аудит проекта перед каждым пунктом.
3. Читать только файлы, необходимые для текущих 1–2 пунктов.
4. Не переписывать рабочие подсистемы без необходимости.
5. Выполнять **ровно по 2 основных пункта за один этап**.
6. После каждых двух закрытых пунктов делать коммит.
7. Формат имени коммита:

```text
19-X
```

где `X` — номер последнего полностью выполненного пункта.

Для этого плана:

```text
19-2
19-4
19-6
```

8. После каждого пункта написать пользователю **ровно одно короткое предложение**: что сделано и какой результат получен.
9. Не писать длинные отчёты, пересказы diff, планы следующего этапа и прочий текст.
10. После **третьего коммита `19-6` обязательно остановиться** и больше ничего не делать без команды пользователя.
11. Если обнаружена проблема вне текущего пункта — кратко записать её, но не уходить исправлять её самостоятельно.
12. Перед каждым коммитом запускать только минимально необходимый набор тестов для изменённых подсистем.
13. Полный тяжёлый benchmark не запускать после каждого небольшого изменения; итоговое сравнение выполняется в пункте 6.

# Пункт 1. Добавить режим `SuperFast / SuperAggressive`

Добавить отдельный режим построения траектории, ориентированный в первую очередь на минимальное время физической печати.

### Что сделать

* Найти текущую конфигурацию режимов печати и построения траекторий.
* Не менять поведение существующего обычного режима.
* Добавить новый режим, например:

```text
superfast
```

или существующее именование проекта, если там уже используется другая система режимов.

* Режим должен включаться явно через существующую конфигурацию/CLI.
* Вынести параметры режима в конфигурацию, а не размазывать magic numbers по коду.
* В этом режиме разрешить повторный проход по уже проведённому участку линии, если это позволяет избежать подъёма пера.
* Стоимость подъёма пера должна считаться значительно выше стоимости короткого повторного движения по бумаге.
* Добавить ограничения, чтобы оптимизатор не создавал бессмысленные длинные повторные проходы.

### Желательный принцип оценки

Оптимизатор должен сравнивать примерно такие стоимости:

```text
pen_up
travel
pen_down
drawing
retrace
```

Причём:

```text
pen_up + travel + pen_down
```

обычно должно считаться значительно дороже короткого:

```text
retrace
```

### Результат

Появился отдельный агрессивный режим скорости, который можно включить без изменения поведения обычной печати.

# Пункт 2. Оптимизировать траекторию внутри буквы

Сейчас главная цель — перестать воспринимать набор сегментов буквы как независимые линии.

### Что сделать

* Для каждой буквы собрать её линии/кривые в связный граф траекторий.
* Найти точки, в которых сейчас происходят подъёмы пера.
* По возможности соединять соседние штрихи без `pen up`.
* Разрешить проход по одному и тому же ребру повторно, если это уменьшает число подъёмов.
* Переставлять направление прохождения отдельных линий:

  * A → B;
  * либо B → A,
    если второе даёт более короткий маршрут.
* Не изменять визуальную геометрию самой буквы без необходимости.
* Учитывать допустимое расстояние для соединения близких концов штрихов.
* Не соединять части, между которыми появилась бы заметная лишняя линия.

### Основная метрика

Приоритет:

```text
1. минимум подъёмов пера;
2. минимум холостых перемещений;
3. минимум общей длины маршрута.
```

### Проверить

Сравнить несколько сложных русских букв и убедиться, что количество `pen up` внутри одной буквы заметно уменьшилось.

# Пункт 3. Оптимизировать не букву, а слово целиком

Следующий уровень оптимизации должен работать уже после формирования всех букв слова.

### Что сделать

После layout букв собрать траектории всего слова и попробовать пройти их как единый граф.

Нужно учитывать:

* конец предыдущей буквы;
* начало следующей буквы;
* соединительные линии рукописного шрифта;
* возможность изменить направление обхода отдельных штрихов;
* возможность повторного прохода по короткому участку;
* стоимость подъёма пера;
* стоимость перемещения к следующей букве.

Оптимизатор должен искать маршрут уже на уровне:

```text
WORD
 ├─ glyph
 ├─ glyph
 ├─ glyph
 └─ glyph
```

а не отдельно оптимизировать каждую букву и потом просто склеивать результат.

### Целевая характеристика

Для обычного связного рукописного слова стремиться к:

```text
1 проход
```

Если геометрия не позволяет:

```text
2 прохода
```

Только сложные случаи могут иметь больше.

### Важно

Не нужно искусственно соединять всё прямыми линиями.

Если соединение визуально портит слово, лучше оставить дополнительный подъём пера.

# Пункт 4. Исправить случайно слишком большие расстояния между словами

Сейчас в части текста слова оказываются расположены значительно дальше друг от друга, хотя в других местах расстояние нормальное.

Нужно найти именно причину, а не просто глобально уменьшить пробел.

### Проверить

* расчёт ширины glyph;
* advance;
* kerning;
* bounding box;
* word width;
* пробел;
* масштабирование;
* rounding;
* случайные handwritten-модификаторы;
* переносы строк;
* alignment/justification;
* преобразование координат после layout;
* накопление смещения по X.

### Что сделать

Разделить понятия:

```text
glyph spacing
letter spacing
word spacing
line alignment
```

Они не должны случайно влиять друг на друга.

Добавить разумные ограничения на ширину пробела.

Если используется рандомизация расстояния между словами, ограничить её небольшим диапазоном относительно базового пробела.

Например, концептуально:

```text
actual_space = base_space * variation
```

где `variation` не может случайно превратить обычный пробел в расстояние шириной с несколько букв.

### Результат

Межсловные интервалы остаются немного естественными, но больше не появляются отдельные аномально огромные промежутки.

# Пункт 5. Исправить знаки препинания

Знаки препинания должны обрабатываться отдельно от соединения букв внутри слова.

Проблемы:

* последняя буква может соединяться со знаком препинания;
* точка/запятая расположены слишком близко к слову;
* оптимизатор может воспринимать знак как следующую букву слова.

### Что сделать

На уровне layout разделить:

```text
letters
punctuation
```

Для последовательности:

```text
слово,
```

траектория должна быть:

```text
написать слово
→ закончить последнюю букву
→ поднять перо
→ перейти к знаку
→ поставить знак
```

Нельзя строить соединительную линию:

```text
последняя буква → ,
```

или:

```text
последняя буква → .
```

### Добавить отдельные параметры

Например концептуально:

```text
punctuation_gap
punctuation_vertical_offset
```

Не обязательно использовать именно эти имена, если в проекте уже есть подходящая структура конфигурации.

### Учитывать отдельно

* `.`
* `,`
* `:`
* `;`
* `!`
* `?`

Кавычки и скобки не ломать существующей логикой, если для них требуется другое позиционирование.

### Результат

Точки и другие знаки визуально отделены от последней буквы, а соединительные линии к ним отсутствуют.

# Пункт 6. Benchmark SuperFast и финальная защита от плохих маршрутов

После реализации провести сравнение обычного и нового режима на одинаковых документах.

### Подготовить минимум три сценария

**Короткая строка**

```text
Привет, как дела?
```

**Строка со сложными русскими буквами**

Например текст с:

```text
ж
м
т
ш
щ
ы
ь
ъ
```

**Несколько строк обычного текста.**

### Для каждого сравнить

* количество `pen up`;
* количество `pen down`;
* число непрерывных проходов на слово;
* длину drawing path;
* длину travel path;
* длину повторных проходов;
* оценочное время;
* количество слов, написанных за:

  * 1 проход;
  * 2 прохода;
  * > 2 проходов.

### Добавить защиту

Если SuperFast создаёт маршрут, который:

* имеет слишком длинный retrace;
* рисует заметную лишнюю линию;
* уходит за допустимую геометрию;
* становится хуже обычного маршрута,

использовать более безопасный вариант маршрута для конкретного glyph/word.

То есть `SuperFast` не должен означать:

```text
любой ценой соединить всё со всем
```

Он должен означать:

```text
минимизировать физическое время там,
где это не портит написанный текст.
```

### Итоговая цель

После оптимизации для обычных рукописных слов большая часть слов должна требовать **не более 1–2 основных непрерывных проходов пера**, а число подъёмов и холостых перемещений должно существенно уменьшиться относительно текущего режима.
