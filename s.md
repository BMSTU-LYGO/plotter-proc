# UPD_Plotter_13 — максимальное ускорение текущего пайплайна

**Главная цель:** значительно уменьшить время конвертации DOCX/PDF в готовый G-code, при этом вообще не ухудшая внешний вид текста, расположение элементов и безопасность печати.

1. **Сделать подробный profiler всех этапов конвертации.** Нужно измерять не только общее время `handwriting`, `simplification` и `build_paths`, а время отдельных функций внутри этих этапов, чтобы точно видеть, какие операции действительно тормозят обработку.

2. **Добавить benchmark-набор документов.** Нужно подготовить несколько фиксированных тестовых документов — короткий текст, длинный текст, таблицы, картинки, формулы и большой многостраничный DOCX — и после каждой оптимизации автоматически сравнивать скорость обработки с предыдущей версией.

3. **Перестать повторно обрабатывать одинаковые буквы при simplification.** Если одна и та же буква используется в документе сотни раз, её базовую геометрию нужно упростить один раз, сохранить как шаблон и дальше только масштабировать, поворачивать и перемещать.

4. **Добавить кеширование готовых glyph path templates.** После преобразования символа шрифта в набор линий нужно хранить уже готовый путь символа, чтобы `build_paths` не строил одинаковую букву заново при каждом её появлении.

5. **Разделить постоянную геометрию буквы и handwriting-искажения.** Нужно сначала использовать дешёвый готовый шаблон символа, а небольшие изменения почерка применять поверх него, чтобы генерация естественного текста не требовала полного пересчёта геометрии.

6. **Ускорить проверку пересечений при соединении букв.** Вместо сравнения новой соединительной линии со всеми линиями текста нужно использовать spatial index или bounding boxes и проверять только расположенные рядом сегменты.

7. **Добавить дешёвую предварительную фильтрацию соединений.** Очевидно плохие варианты соединения букв нужно отбрасывать до запуска дорогих геометрических проверок, используя расстояние, направление выхода из буквы и положение следующей буквы.

8. **Распараллелить обработку страниц.** После того как документ уже разбит на страницы, тяжёлую обработку разных страниц нужно выполнять одновременно в нескольких процессах, сохраняя итоговый порядок страниц.

9. **Добавить параметр количества worker-процессов.** Пользователь должен иметь возможность использовать `--workers auto`, `--workers 1`, `--workers 4` и другие значения, чтобы на мощном компьютере задействовать все доступные ядра.

10. **Распараллелить компиляцию centerline-шрифта по символам.** Буквы шрифта почти независимы друг от друга, поэтому разные glyph нужно переводить в centerline одновременно в нескольких процессах.

11. **Не обрабатывать весь шрифт, если нужны только несколько символов.** Если в документе используются только 50 символов, система должна компилировать только их, а остальные добавлять в кеш позже по необходимости.

12. **Разбить кеш шрифта на отдельные glyph-файлы.** Вместо одного большого объекта нужно хранить каждую букву отдельно, чтобы быстро читать, обновлять и пересобирать только необходимые символы.

13. **Переиспользовать промежуточные данные centerline-алгоритма.** Если разные способы построения средней линии используют одну растровую маску, distance transform или другие одинаковые данные, их нужно вычислять только один раз.

14. **Добавить fast path для уже хорошо обработанных букв.** Если первый алгоритм centerline сразу даёт качественный результат, не нужно запускать дополнительные дорогие алгоритмы сравнения.

15. **Сократить количество генерируемых debug-артефактов в обычном режиме.** SVG, промежуточные JSON, изображения и подробные отчёты нужно создавать только в debug/audit режимах, чтобы обычная конвертация не тратила время на ненужную запись файлов.

16. **Рассмотреть перенос самых горячих геометрических функций на C++.** После profiler нужно выбрать только действительно дорогие функции вроде collision detection, simplification и segment intersection и реализовать их через C++/pybind11, не переписывая весь проект.

17. **Проверять эквивалентность результата после каждой оптимизации.** Ускоренная версия должна автоматически сравниваться со старой по количеству страниц, расположению элементов, геометрии и safety-проверкам, чтобы ускорение никогда не ломало качество.

18. **Добавить итоговый performance report.** После выполнения benchmark система должна показывать время каждого этапа, общее время, процент ускорения и количество использованных процессов.

# UPD_Plotter_14 — архитектура, кеширование и поддерживаемость проекта

**Главная цель:** привести уже большой проект к архитектуре, в которой новые возможности можно добавлять без постоянного усложнения старого кода.

1. **Разбить pipeline на явно определённые этапы.** Чтение документа, layout, построение геометрии, handwriting, simplification, routing и генерация G-code должны стать отдельными stage с чётко определёнными входами и выходами.

2. **Сделать pipeline в виде DAG зависимостей.** Каждый этап должен знать только данные предыдущих этапов, чтобы можно было повторно запускать одну часть обработки, не пересчитывая весь документ.

3. **Добавить кеш результата каждого большого этапа.** Если исходный документ и настройки layout не изменились, не нужно заново читать DOCX и разбивать его на страницы только потому, что пользователь поменял скорость печати.

4. **Сделать fingerprint для каждого stage.** Система должна определять, какие именно настройки влияют на конкретный этап, и инвалидировать кеш только тогда, когда действительно изменились связанные с ним параметры.

5. **Разделить слишком большие Python-модули.** Большие файлы вроде paginator, pipeline и handwriting нужно постепенно разбить на более маленькие модули с одной понятной ответственностью.

6. **Выделить отдельный слой document model.** DOCX и PDF должны преобразовываться в общий внутренний формат документа, чтобы остальная система не зависела напрямую от особенностей конкретного входного формата.

7. **Выделить отдельный layout layer.** Расчёт положения текста, таблиц, формул, изображений и страниц должен происходить независимо от последующей генерации handwriting geometry.

8. **Выделить отдельный geometry layer.** Все операции над линиями, кривыми, bounding boxes, intersections и simplification нужно собрать в одном месте, чтобы они не дублировались между разными частями проекта.

9. **Создать собственный формат скомпилированного шрифта `.plotfont`.** В нём нужно хранить уже готовые centerline glyphs, anchors, порядок strokes, метрики и дополнительную информацию, необходимую плоттеру.

10. **Добавить версионирование внутренних форматов.** `paths.json`, compiled font, document model и job-файлы должны иметь номер schema version, чтобы будущие изменения не ломали старые кеши и документы.

11. **Добавить единый cache manager.** Вместо самостоятельной работы каждого модуля с папками и файлами должен существовать общий механизм чтения, записи, проверки версий и очистки кеша.

12. **Добавить автоматическую очистку старого кеша.** Система должна уметь удалять устаревшие версии, повреждённые entries и давно неиспользуемые данные.

13. **Разделить настройки машины, бумаги, ручки и почерка.** Вместо одного большого конфига должны существовать независимые профили `machine`, `paper`, `pen` и `handwriting`.

14. **Сделать нормальную систему presets.** Пользователь должен иметь возможность написать `--preset fast`, `--preset quality` или `--preset debug`, а система сама выставит соответствующий набор параметров.

15. **Ввести уровни генерации артефактов.** Режимы `minimal`, `normal`, `debug` и `audit` должны определять, сколько промежуточных файлов сохраняется после конвертации.

16. **Добавить `make audit`.** Одна команда должна запускать lint, тесты, smoke, integration tests, determinism, safety scan и основные benchmarks.

17. **Настроить GitHub Actions.** Каждый pull request должен автоматически проходить базовые тесты, а более тяжёлые benchmark и full-font проверки можно запускать отдельно или по расписанию.

18. **Добавить golden geometry tests.** Для важных документов нужно хранить эталонную геометрию и автоматически обнаруживать неожиданные визуальные изменения после изменения алгоритмов.

19. **Добавить fuzz/property tests для документов.** Случайные комбинации таблиц, абзацев, пустых элементов, Unicode и изображений должны проверяться хотя бы на отсутствие crash, NaN и выхода за рабочую область.

20. **Добавить единый diagnostic report при ошибке.** Если документ не удалось обработать, пользователь должен получать понятное сообщение с этапом ошибки, входным элементом и рекомендацией, а не длинный Python traceback.

# UPD_Plotter_15 — Handwriting 2.0 и реалистичность почерка

**Главная цель:** сделать результат менее похожим на компьютерный шрифт и больше похожим на текст, написанный одной и той же рукой.

1. **Добавить несколько вариантов написания одной буквы.** Для каждой часто используемой буквы можно хранить несколько немного отличающихся centerline-вариантов и выбирать между ними при написании текста.

2. **Сделать выбор вариантов детерминированным через seed.** Один и тот же документ с одинаковым `--seed` должен каждый раз генерировать абсолютно одинаковый почерк.

3. **Добавить небольшое изменение размера букв.** Высота и ширина отдельных символов должны слегка отличаться в допустимых пределах, чтобы повторяющиеся буквы не выглядели клонами.

4. **Добавить небольшое изменение наклона символов.** Наклон букв должен немного колебаться, но оставаться характерным для выбранного handwriting profile.

5. **Добавить колебания baseline.** Буквы и слова можно слегка поднимать и опускать относительно идеальной строки, имитируя реальный почерк человека.

6. **Добавить изменение расстояния между буквами.** Интервалы внутри слов должны быть немного неодинаковыми, но не настолько, чтобы ухудшалась читаемость.

7. **Добавить изменение расстояния между словами.** Пробелы также должны иметь небольшую естественную вариативность.

8. **Не генерировать variation полностью независимо для каждой буквы.** Изменения должны иметь корреляцию внутри слова и строки, потому что человек обычно пишет несколько соседних букв с похожим наклоном и размером.

9. **Добавить variation уровня строки.** Каждая строка может иметь очень небольшое собственное смещение, наклон или изменение высоты текста.

10. **Добавить variation уровня слова.** Слово целиком может быть чуть сжато, растянуто или наклонено, после чего поверх этого применяются небольшие изменения отдельных букв.

11. **Улучшить entry/exit anchors каждой буквы.** Для каждого glyph нужно определить естественную точку входа и выхода пера, чтобы соединения строились не просто между ближайшими точками.

12. **Добавить информацию о направлении касательной в начале и конце буквы.** Соединительная линия должна продолжать естественное направление предыдущего stroke, а не создавать резкий угол.

13. **Сделать специальные правила для пар букв.** Часто встречающиеся сочетания вроде `ст`, `пр`, `ов`, `ть` и другие могут иметь собственную preferred connection geometry.

14. **Добавить handwriting kerning.** Расстояние между буквами нужно определять не только по bounding box, но и по реальной форме соседних glyphs.

15. **Добавить human stroke order.** Для сложных кириллических букв нужно определить порядок, в котором человек обычно рисует их линии.

16. **Улучшить problematic glyphs вручную или полуавтоматически.** Особенно сложные символы вроде `ъ`, `ь`, `ы`, `ж`, `ф` и других можно корректировать специальными topology rules.

17. **Оптимизировать stroke routing внутри буквы с учётом следующей буквы.** Если у символа есть несколько допустимых способов пройти strokes, нужно выбирать тот, который удобнее продолжить следующим символом.

18. **Добавить стоимость подъёма пера в routing algorithm.** При выборе маршрута нужно учитывать не только пройденное расстояние, но и то, что каждый подъём ручки физически дорогой.

19. **Разрешить небольшой безопасный retrace.** Иногда повторное прохождение короткого уже написанного участка лучше, чем подъём пера и длинный холостой переезд.

20. **Создать полноценный handwriting profile.** Профиль должен содержать не только TTF, но также variation settings, anchors, stroke order, connection rules, spacing и другие характеристики конкретного почерка.

21. **Добавить режимы реалистичности.** Например `clean`, `natural` и `rough`, чтобы пользователь мог выбирать между аккуратным и более живым почерком.

22. **Добавить visual regression corpus.** Нужно собрать набор русских слов и предложений, включающих проблемные сочетания букв, и использовать его для проверки качества новых алгоритмов.

# UPD_Plotter_17 — автоматизация самого плоттера

**Главная цель:** убрать ручные операции между страницами и значительно ускорить физическую работу устройства.

2. **Сделать отдельную команду Pen Up/Pen Down.** Software layer не должен знать, используется Z или servo — он должен просто отдавать абстрактные команды поднять или опустить ручку.

3. **Добавить pen profile.** Для разных ручек нужно хранить параметры прижима, скорость рисования, задержку после касания бумаги и другие физические настройки.

4. **Добавить acceleration-aware расчёт времени.** Оценка длительности должна учитывать реальные ускорения Ender 3, потому что на коротких линиях принтер не успевает разогнаться до указанного feedrate.

5. **Оптимизировать motion planner под короткие strokes.** Скорость и acceleration нужно выбирать так, чтобы плоттер двигался максимально быстро без появления дрожания, пропуска шагов и ухудшения почерка.

6. **Добавить автоматическую подачу бумаги.** После окончания страницы внешний механизм должен убрать готовый лист и подать следующий.

7. **Не использовать фиксированный `sleep` между страницами.** Вместо ожидания определённого количества секунд плоттер должен получать реальное подтверждение, что новый лист уже находится на месте.

8. **Сделать handshake между плоттером и механизмом подачи.** Например плоттер отправляет `PAGE_DONE`, feeder отвечает `FEEDING`, а после окончания подачи отправляет `PAGE_READY`.

9. **Добавить датчик наличия бумаги.** Система должна проверять, действительно ли новый лист оказался в рабочей зоне.

10. **Добавить обнаружение ошибки подачи.** Если бумага застряла или новый лист не появился, плоттер должен остановиться, а не продолжать писать по столу.

11. **Добавить safe position для головы.** Перед заменой листа ручка должна автоматически подниматься и уезжать в безопасный угол.

12. **Добавить контроллер feeder на Arduino/ESP32.** Управление роликами и датчиками лучше вынести в отдельный простой контроллер, взаимодействующий с основным софтом по понятному протоколу.

13. **Добавить процедуру автоматической калибровки бумаги.** Перед печатью плоттер должен уметь проверить несколько точек и определить реальное положение рабочей области.

14. **Добавить камеру над рабочей зоной.** Камера сможет определять четыре угла листа и видеть, если бумага лежит не идеально ровно.

15. **Добавить коррекцию координат по положению листа.** Если лист немного повернут, система должна применить transform/homography и всё равно писать текст параллельно краям бумаги.

16. **Добавить контроль выхода за лист.** После определения реального положения бумаги каждая команда движения должна дополнительно проверяться относительно фактических границ листа.

17. **Добавить обнаружение снятого или сместившегося листа.** Перед началом следующей страницы камера или датчики могут подтверждать, что бумага не уехала.

18. **Подготовить протокол для будущих аппаратных модулей.** Feeder, servo, камера и дополнительные устройства должны взаимодействовать через единый abstraction layer, а не отдельные хаки в pipeline.

### Желаемый результат UPD_Plotter_17

Можно положить пачку бумаги, запустить многостраничный документ и получить готовую стопку страниц **без ручной замены каждого листа**.

# UPD_Plotter_18 — расширенная поддержка документов и графики

**Главная цель:** увеличить количество типов контента, которые можно качественно переносить из обычных документов на бумагу.

1. **Добавить SVG как полноценный входной формат.** SVG нужно обрабатывать напрямую как векторную геометрию, не превращая его сначала в растровое изображение.

2. **Сохранять vector geometry максимально долго.** Линии, схемы и графики из SVG/PDF не нужно растрировать, если их можно сразу преобразовать в paths плоттера.

3. **Улучшить поддержку маркированных списков DOCX.** Буллеты должны сохранять правильные отступы и положение относительно текста.

4. **Улучшить нумерованные списки.** Номер, отступ первой строки и переносы длинного пункта должны соответствовать исходному Word-документу.

5. **Добавить поддержку superscript и subscript.** Обычные надстрочные и подстрочные символы должны правильно масштабироваться и располагаться относительно строки.

6. **Расширить поддержку headers и footers.** Верхние и нижние колонтитулы должны повторяться на соответствующих страницах.

7. **Улучшить footnotes.** Сноска должна переноситься в нижнюю часть нужной страницы и иметь правильную связь с номером в основном тексте.

8. **Добавить поддержку нескольких колонок.** Документы с двумя или более колонками должны сохранять исходный порядок чтения и расположение текста.

9. **Улучшить nested tables.** Таблица внутри ячейки другой таблицы должна корректно масштабироваться и переноситься на бумагу.

10. **Улучшить borders и другие элементы оформления таблиц.** Нужно поддерживать разные типы границ и корректно определять, какие из них вообще стоит рисовать плоттером.

11. **Расширить поддержку DrawingML shapes.** Стрелки, прямоугольники, окружности, линии и другие стандартные фигуры Word нужно преобразовывать непосредственно в векторные пути.

12. **Улучшить positioning floating images.** Картинки должны сохранять положение относительно текста, а обтекание должно максимально соответствовать исходному документу.

13. **Улучшить PDF semantic reconstruction.** Нужно лучше определять, какие элементы PDF являются текстом, формулами, таблицами, схемами и обычными рисунками.

14. **Уменьшить количество low-confidence предупреждений PDF.** Система должна увереннее классифицировать математические элементы и сложную векторную графику.

15. **Расширить поддержку математических формул.** Нужно увеличивать количество LaTeX/OMML конструкций, которые переводятся в нормальную centerline/vector geometry.

16. **Добавить специализированный math font pipeline.** Математические символы можно компилировать и кешировать так же, как обычный handwriting font.

17. **Добавить режим `outline` для изображений.** Система должна выделять основные внешние контуры рисунка и превращать их в линии плоттера.

18. **Добавить режим `centerline` для схем и штриховых рисунков.** Толстые линии изображения нужно преобразовывать в одну центральную траекторию.

19. **Добавить hatching.** Затемнённые области изображения можно передавать параллельными штрихами с плотностью, зависящей от яркости.

20. **Добавить cross-hatching.** Для более тёмных участков можно использовать несколько пересекающихся направлений штрихов.

21. **Оптимизировать порядок рисования изображения.** После векторизации нужно минимизировать холостые перемещения между отдельными линиями рисунка.

22. **Добавить несколько цветов.** Документ можно разделять на цветовые слои и останавливать плоттер в нужный момент для замены ручки.

23. **Добавить команды смены ручки между слоями.** Например после синего слоя головка паркуется, печать ставится на паузу и пользователь получает сообщение поставить красную ручку.

24. **Добавить OCR как отдельный optional pipeline.** Отсканированные PDF и фотографии страниц можно будет преобразовывать обратно в структурированный текст и затем печатать обычным handwriting pipeline.

25. **Не смешивать OCR с обычным PDF parser.** Для нормального PDF нужно продолжать использовать исходные текстовые и векторные данные, а OCR запускать только тогда, когда документ действительно является сканом.

### Желаемый результат UPD_Plotter_18

Плоттер сможет нормально принимать не только простой текстовый DOCX, но и **сложные учебные документы со списками, формулами, схемами, таблицами, изображениями и SVG-графикой**.
