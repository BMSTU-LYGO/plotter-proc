# UPD_Plotter_13 — ускорение pipeline

## Общие правила для Codex

Работай **в той ветке, в которой задача была запущена**: не создавай новую ветку и не переключайся на другую.

Главная цель — **максимально ускорить конвертацию документа без изменения результата, качества геометрии и безопасности G-code**.

Экономь токены: сначала изучи только необходимые entrypoints и файлы, используй `rg`, `git diff`, существующие тесты и profiler, не перечитывай весь репозиторий перед каждым пунктом и не создавай длинные отчёты.

После каждого пункта пиши в чат **ровно одно короткое предложение** в формате:

`13-X: сделано <что изменено>, проверено <чем>.`

Не описывай ход рассуждений, содержимое diff, найденные файлы и промежуточные эксперименты, если нет ошибки, которая мешает продолжать.

Выполняй **строго по 2 пункта за один коммит**.

После пунктов `1-2` сделать commit:

```bash
git commit -m "13-2"
```

После `3-4`:

```bash
git commit -m "13-4"
```

и так далее — **`13-X`, где X является номером последнего полностью закрытого пункта**.

Перед каждым коммитом запускай только необходимые targeted tests; более широкий набор тестов запускай после завершения очередного блока из 6 пунктов.

**После каждых 3 коммитов обязательно остановись и ничего дальше не делай.**

То есть точки остановки:

* после `13-6`;
* после `13-12`;
* после `13-18`.

На промежуточной остановке написать только:

`Остановился после 13-X. Готов продолжить с 13-(X+1).`

Не начинать следующие пункты самостоятельно.

Если один пункт нельзя закончить корректно, **не коммить незавершённую реализацию и не переходи к следующему блоку**.

## Критичные ограничения для Codex

Не делать массовый рефакторинг «заодно»: **UPD_Plotter_13 посвящён производительности**, архитектурная перестройка будет отдельным этапом.

Не менять визуальное поведение специально ради ускорения: результат при одинаковых входных данных и seed должен оставаться эквивалентным в рамках существующих допусков.

Не добавлять новую пользовательскую функциональность, если она напрямую не нужна для performance.

Не делать C++ первым решением проблемы: сначала profiler → алгоритмическое устранение повторных вычислений → только потом native hotspot.

Не создавать новые длинные `.md`-отчёты после каждого пункта и не записывать в чат огромные benchmark/diff; достаточно одной строки на пункт и итоговых цифр на контрольной остановке.

**Итого получится ровно 9 коммитов:**

`13-2 → 13-4 → 13-6 → STOP → 13-8 → 13-10 → 13-12 → STOP → 13-14 → 13-16 → 13-18 → STOP`.

Такой вариант хорошо подходит для Codex: у него всегда только **два текущих пункта в контексте**, после трёх небольших коммитов он останавливается, а большие архитектурные изменения не смешиваются с задачей ускорения.
