# UPD_Plotter_14 — архитектура, кеширование и поддерживаемость проекта

## Общие правила для Codex

Работай **строго в той ветке, в которой задача была запущена**. Не создавай новую ветку и не переключайся на другую.

Главная цель `UPD_Plotter_14` — **привести текущий проект к модульной архитектуре, уменьшить связанность компонентов и сделать повторные запуски pipeline максимально дешёвыми за счёт stage cache**, не меняя существующее пользовательское поведение.

### Экономия токенов

Codex должен максимально экономить контекст и токены:

* не читать весь репозиторий целиком;
* сначала использовать `rg`, `find`, `git diff`, существующие тесты и точечный просмотр файлов;
* открывать только файлы, относящиеся к текущим двум пунктам;
* не перечитывать уже изученные файлы без необходимости;
* не писать отдельные длинные отчёты;
* не создавать документацию, если она не нужна для работы кода;
* использовать существующие модели и abstractions, если они подходят;
* не делать рефакторинг соседнего кода «заодно».

После каждого пункта писать в чат **ровно одно короткое предложение**:

`14-X: сделано <что изменено>, проверено <чем>.`

Не описывать chain of thought, подробности реализации, содержимое diff и список изменённых файлов.

# Критичные ограничения UPD_Plotter_14

### 1. Не переписывать проект целиком

Это **постепенный рефакторинг существующего рабочего проекта**, а не создание новой архитектуры с нуля.

---

### 2. Не смешивать с UPD_Plotter_15

В этом обновлении **не улучшать визуально почерк**, не добавлять новые алгоритмы соединения букв, variation и stroke order.

Если текущий алгоритм выглядит неидеально, но работает так же, как до `UPD_Plotter_14`, это не задача данного этапа.

---

### 3. Не смешивать с пользовательскими фичами

Не добавлять Web UI, direct printing, OCR, новые форматы документов или аппаратные функции.

---

### 4. Backward compatibility важнее красоты архитектуры

Существующие CLI-команды, основные конфиги и normal workflow должны продолжать работать либо иметь очень простой compatibility layer.

---

### 5. Не создавать abstraction ради abstraction

Каждый новый interface/class/module должен устранять существующую связанность, дублирование или позволять кешировать конкретный stage.

Если abstraction не даёт практической пользы сейчас — не создавать её.

---

### 6. Не дробить файлы механически

Не нужно превращать один большой файл в двадцать маленьких файлов без логической причины.

Разделять только по ответственности.

---

### 7. Не кешировать всё подряд

Кешировать только дорогие и стабильные этапы, где стоимость сериализации заметно меньше стоимости повторного вычисления.

---

### 8. Любой persistent cache считается disposable

Удаление `.cache` не должно ломать проект: всё необходимое должно автоматически восстановиться из исходных данных.

---

### 9. Cache write должен быть безопасным

Не оставлять валидным частично записанный entry после crash; использовать atomic replacement или существующий безопасный механизм.

---

### 10. Determinism сохранить

При одинаковом:

```text
document
config
font
seed
version
```

результат должен быть одинаковым независимо от того, пришли промежуточные данные из кеша или были рассчитаны заново.

---

# Что в итоге должен дать UPD_Plotter_14

После завершения архитектура должна примерно логически выглядеть так:

```text
                 INPUT
                   │
                   ▼
            ┌─────────────┐
            │   Reader    │
            └──────┬──────┘
                   ▼
             DocumentModel
                   │
             [stage cache]
                   │
                   ▼
            ┌─────────────┐
            │   Layout    │
            └──────┬──────┘
                   ▼
              LayoutModel
                   │
             [stage cache]
                   │
                   ▼
            ┌─────────────┐
            │  Geometry   │
            └──────┬──────┘
                   ▼
                 Paths
                   │
             [stage cache]
                   │
                   ▼
            ┌─────────────┐
            │ Handwriting │
            └──────┬──────┘
                   ▼
            Final Geometry
                   │
             [stage cache]
                   │
                   ▼
            ┌─────────────┐
            │   G-code    │
            └──────┬──────┘
                   ▼
               OUTPUT
```

Ключевой практический результат должен быть таким:

```text
Поменял DOCX
→ пересчиталось всё.

Поменял формат A5 → A4
→ parsing взялся из кеша,
→ layout и ниже пересчитались.

Поменял handwriting
→ parsing и layout взялись из кеша,
→ handwriting и ниже пересчитались.

Поменял скорость движения
→ документ, layout и geometry взялись из кеша,
→ практически сразу пересоздался только G-code.
```
